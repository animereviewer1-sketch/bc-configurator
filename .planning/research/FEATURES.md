# Feature Research

**Domain:** Bondage Club (BC) companion/configurator tooling — runtime game-code/API inventory scan + mod discovery
**Researched:** 2026-09-12
**Confidence:** MEDIUM-HIGH (core mod-SDK facts verified against primary source; some mod globals unverified — see Gaps)

## Feature Landscape

### Table Stakes (Users Expect These)

For a "game code scan" feature to be useful at all (not a toy), it must reliably answer "what can I hook into that I'm not already using?" without breaking anything.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| **Core game global/function probe** (`Player`, `ChatRoom`, `ServerSend`, `InventoryGet`, `InventoryWear`, `CharacterGetCurrent`, etc.) | This is the entire premise of the scan — without it there's no inventory | LOW | Loader already reads several of these (`loader.js` cache builder). Extend the existing probe list; a simple `typeof window[name]` + `.toString().slice(0,200)` signature capture per known name is enough — no need to walk the whole `window` object. |
| **Asset catalog extraction** (groups, item properties, lock types, colors, layers) | Bot actions and outfit features are built on asset data; incomplete catalog = incomplete bot action list | MEDIUM | Loader already builds a cache from `Asset[]`/`AssetGroup[]` (Architecture: "Loader builds cache by iterating BC's Asset array"). This is additive: capture property *names* (e.g. `Effect`, `Block`, `Prerequisite`) that exist on assets but aren't currently read into the tool's cache shape. |
| **Chat hook / event enumeration** | Bots react to chat; the scan must show what hookable message/event surface exists, not just item mechanics | LOW-MEDIUM | Vanilla BC exposes `ChatRoomRegisterMessageHandler({ Description, Priority, Callback })` as a first-class hook API for exactly this purpose (confirmed against a BC core-code refactor merge request — see Sources). The scan should record that this function exists and, if the game exposes an internal registry of already-registered handlers, list handler descriptions (read-only; do not register a probe handler that could double-fire in a live room). |
| **bcModSdk mod registry read** (`window.bcModSdk.getModsInfo()`) | This is the single highest-value, lowest-risk mod-discovery call available — it enumerates every mod that plays nice with the ecosystem's shared SDK | LOW | Verified directly from `bondage-club-mod-sdk` source (`modRegistry.ts`/`sdkApi.ts`): `bcModSdk.getModsInfo()` returns `[{ name, fullName, version, repository }, …]` for every SDK-registered mod (HIGH confidence — primary source). Only covers mods that opted into the SDK; not a complete mod census (see Gaps). |
| **bcModSdk patch/hook registry read** (`window.bcModSdk.getPatchingInfo()`) | Shows exactly which *game functions* are already hooked/patched and by which mod — directly answers "what's already claimed, what's free to hook" | LOW | Verified from source (`patching.ts`): returns a `Map<functionName, { name, original, originalHash, sdkEntrypoint, currentEntrypoint, hookedByMods: string[], patchedByMods: string[] }>`. This is arguably more valuable than a raw global dump because it's pre-filtered to "functions someone found worth hooking." |
| **Known-mod fallback probes** (`window.bcx`, `window.mbs`, `window.LSCG_DB`/LSCG globals, WCE/FBC-style globals) | Not every popular mod uses bcModSdk for its *public* surface — BCX and MBS expose their own dedicated globals in addition to (or instead of) SDK registration | LOW-MEDIUM | Verified: BCX exposes `window.bcx` (`version`, `versionParsed`, `isDevel`, `getModApi()`, event emitter) — from BCX's own `bcxExternalInterface.d.ts`. MBS exposes `globalThis.mbs` (`MBS_VERSION`, `API_VERSION.major`, `wheelEvents`) — from MBS's own API README. `LSCG_DB` is already consumed by this tool's existing outfit-scan feature (per PROJECT.md) — treat it as a known/used probe, not a new discovery. Needs a maintained probe list per mod since there's no universal registry (see bcModSdk gap above). |
| **"Already used by tool" baseline** | Without this, every scan result looks "new" forever — the diff is the entire point of the requirement (PROJECT.md: "Vorschlagsliste neuer Bot-Aktionen/-Trigger…") | MEDIUM | Build a static manifest of symbols/asset-properties/chat-hooks the tool's own code currently references (can be generated by grepping `bot-data.js`, `bot-engine.js`, `loader.js`, feature modules for known BC identifiers) and compare it against the runtime scan. This manifest needs a human-curated seed since static grep will miss dynamically-constructed names. |
| **Read-only scan, no invocation of discovered functions** | Calling unknown functions with synthesized arguments can change player/room state, trigger anti-cheat heuristics, or desync chat — unacceptable for a tool whose core value is "never lose/break data" | LOW | Enforce at the loader level: scan only reads `typeof`, `.toString()`, `.name`, `.length` (arity) and known safe getters (`Player.Appearance`, `Asset` array, `bcModSdk.getModsInfo()`). Never calls a function whose behavior isn't already known and intentional. |
| **Versioned snapshot storage, no silent overwrite** | Matches the project's core value directly — scans are exactly the kind of scanned/gathered data the "never lose data" rule protects | LOW-MEDIUM | Store each scan as a new timestamped entry (mirrors the existing outfit-scan versioning pattern already in the codebase for `LSCG_DB`); never overwrite a prior scan snapshot automatically. |
| **Manual delete with confirmation dialog** | Explicit Active requirement in PROJECT.md; general pattern for any tool whose core promise is "nothing is lost automatically" | LOW | Same UI pattern the Stabilisierung milestone item already calls for on images/outfits — reuse the same confirm-dialog component for scan snapshots rather than inventing a second pattern. |
| **Visible quota-exceeded error on save** | Explicit Active requirement (`idbSet()` must surface `QuotaExceededError`); scans can be large (full asset catalog + multiple mods), making this the feature most likely to actually trigger the bug | LOW | Wrap the scan-save path through the same fixed `idbSet()`; additionally call `navigator.storage.estimate()` before a full-catalog scan and warn proactively if usage is already close to quota (MDN/StorageManager pattern — general web-platform best practice, not BC-specific). |

### Differentiators (Competitive Advantage)

No known BC companion tool currently does automated mod-API discovery + diff-against-own-usage. This is where the feature actually earns its complexity budget.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| **Searchable Scan-Tab with "used" vs "new" badges** | Directly requested in PROJECT.md; lets the author browse hundreds of discovered symbols without re-reading raw JSON dumps | MEDIUM | Follow the established pattern from OpenAPI/schema-diff tooling (oasdiff, OpenAPI Diff Viewer): group by category (Globals / Chat Hooks / Asset Properties / Mods), tag each row `used` / `new` / `changed-since-last-scan`, make the list filterable by category and by mod. A precedent exists *inside* the BC ecosystem itself: MBS ships "a new screen showing all items added in the current BC version" — i.e. a diff-against-baseline UI is already a recognized pattern among BC's own power users, not an invented one. |
| **Suggested bot actions/triggers derived from new discoveries** | Explicit Active requirement ("Vorschlagsliste neuer Bot-Aktionen/-Trigger"); turns a passive inventory into an actionable backlog | MEDIUM | Map discovered symbols to the existing Trigger/Action/Event type system in `bot-data.js` heuristically (e.g. a new `ChatRoomRegisterMessageHandler`-style hook → suggest a new Trigger type stub; a new asset property → suggest a new Action parameter). Always require manual review/creation — never auto-generate live bot code from a suggestion (see Anti-Features). |
| **Per-mod compatibility awareness in the Bot Editor** | Bots that assume a mod's presence (e.g. an LSCG-specific action) silently no-op or error if that mod isn't loaded in a given session; surfacing this at edit/execute time prevents confusing failures | MEDIUM | Cross-reference `bcModSdk.getModsInfo()` + known-mod probes against which bot actions reference mod-specific globals; show a warning badge in the Bot Editor when a bot's dependencies aren't present in the most recent scan. |
| **Hooked-function conflict view** | Shows which game functions are already hooked by which mods (from `bcModSdk.getPatchingInfo()`) before the tool's own EXEC-injected bot code does its own monkey-patch-style watchers (per Architecture's "anti-strip/no-strip watchers" in `bot-engine.js`) | MEDIUM | Purely informational at first — flag potential collisions between the tool's injected code and mod hooks on the same function name, so the author can debug "why did my bot's watcher stop firing" faster. |
| **Historical scan diffing** (compare scan snapshot from date A vs date B) | BC's core game updates periodically and mods update independently; being able to answer "what changed since I last scanned" is more valuable over time than any single snapshot | MEDIUM-HIGH | Defer until versioned snapshot storage (table stakes) is stable and the persistence-layer extraction (Entflechtung milestone) has happened — diffing two arbitrary snapshots is straightforward once snapshots are cleanly stored, but not worth building on top of today's monolithic `items.js` persistence. |

### Anti-Features (Commonly Requested, Often Problematic)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|------------------|-------------|
| **Eval-based fuzzing / auto-invoking discovered functions to learn their behavior** | Tempting way to "fully" document an unknown function's real signature/effects | Can mutate player/room/chat state unpredictably, desync other players in a live room, trip BC's own anti-cheat/rate-limit heuristics, or corrupt curse/lock state that this tool promises never to lose. Explicitly flagged as an anti-feature by the milestone context itself. | Static reflection only: `typeof`, `.toString()`, arity, known-safe read-only getters. If real behavior must be understood, the author manually tests in a private/test room and records findings — not the tool. |
| **Bundling actual BC/mod source code in the repository** | Would make static analysis/autocomplete easier and avoid depending on the user having a live game tab open | Directly excluded by PROJECT.md Out of Scope ("Kopie des BC-Gamecodes im Repo"); BC and its mods update independently of this tool, so a bundled copy goes stale immediately and creates a maintenance burden with zero runtime benefit | Runtime-only export via the existing loader bridge; optionally accept a locally-provided reference file as a *supplementary* read (already called out in PROJECT.md as acceptable), never as the primary source of truth |
| **Fully automatic bot-code generation from scan results** | Would look impressive — "click a button, get a working bot action" | The tool's core value is data safety, not speed; auto-generated code injected via EXEC without review is the highest-risk path in the entire system (arbitrary `eval()` in the game tab) — a wrong auto-generated snippet could corrupt curse state, spam chat, or break restraints in a live room | Suggestions only — pre-filled skeletons the author reviews and completes manually in the existing Bot Editor UI, same trust boundary as any other bot |
| **Deep call-tracing / wrapping every game function to observe live behavior** | Would catch dynamic behavior static reflection misses | Wrapping hundreds of game functions for tracing is exactly the kind of invasive monkey-patching that conflicts with other mods' hooks (the same failure mode `bcModSdk.hookFunction` exists to prevent), and adds real performance/stability risk to a live game session | Rely on `bcModSdk.getPatchingInfo()` for what's *already* being hooked by others (no extra risk, since that data already exists), plus static reflection for the rest |
| **Automatic pruning/expiry of old scan snapshots ("keep last N")** | Reasonable-sounding storage hygiene | Directly conflicts with the project's core value — no automatic deletion, ever, of scanned data | Manual delete with confirmation (table stakes); visible quota warnings before storage fills up, so the author prunes deliberately |
| **Continuous/background polling scans while connected to a room** | Would keep the inventory "always fresh" | Unnecessary overhead per postMessage round-trip and per-scan asset-catalog read; scans are for API discovery (which changes on BC/mod update cadence, i.e. rarely), not live game state (which the existing room-scan/outfit-scan features already handle) | On-demand scan triggered by an explicit button in the new Scan-Tab, same interaction model as the existing "Load Cache" flow |

## Feature Dependencies

```
Core global/function probe
    └──requires──> Loader Bridge EXEC/GET_CACHE channel (existing)

Asset catalog extraction ──enhances──> Core global/function probe

Chat hook enumeration ──requires──> Loader Bridge EXEC/GET_CACHE channel (existing)

bcModSdk registry read ──requires──> Loader Bridge EXEC/GET_CACHE channel (existing)
bcModSdk patch registry read ──requires──> bcModSdk registry read (both come from same window.bcModSdk object)

Known-mod fallback probes ──enhances──> bcModSdk registry read
    (fallback probes catch mods that don't register with the SDK)

"Already used by tool" baseline manifest
    └──requires──> Core global/function probe + Asset catalog extraction + Chat hook enumeration
                       (need a runtime scan shape before you can diff against it)

Versioned snapshot storage ──requires──> idbSet() QuotaExceededError handling (Stabilisierung milestone)
Manual delete with confirmation ──requires──> Versioned snapshot storage
Visible quota-exceeded error ──requires──> idbSet() fix (Stabilisierung milestone, already planned)

Searchable Scan-Tab UI (used vs new badges)
    └──requires──> "Already used by tool" baseline manifest + Versioned snapshot storage

Suggested bot actions/triggers ──requires──> Searchable Scan-Tab UI + existing bot-data.js type system

Per-mod compatibility awareness in Bot Editor ──requires──> bcModSdk registry read + Known-mod fallback probes

Hooked-function conflict view ──requires──> bcModSdk patch registry read

Historical scan diffing ──requires──> Versioned snapshot storage + Persistence-layer extraction (Entflechtung milestone)
```

### Dependency Notes

- **Everything requires the existing Loader Bridge:** every scan capability is just a new read performed inside `loader.js` and shipped back over the existing `postMessage` channel — no new trust boundary, no new bridge protocol needed, consistent with the "Gamecode-Inventar zur Laufzeit über den Loader exportieren" decision already recorded in PROJECT.md.
- **bcModSdk registry read enables the patch registry read** because both come off the same `window.bcModSdk` object populated by `sdkApi.ts`'s `CreateGlobalAPI()` — if one is present, the other is too; no separate feature-detection needed.
- **Known-mod fallback probes are not optional** — `bcModSdk.getModsInfo()` only lists mods that opted into SDK registration. BCX exposes `window.bcx` independently; MBS exposes `globalThis.mbs` independently. Relying on the SDK registry alone would under-report the mod landscape.
- **The diff/baseline manifest blocks the entire Scan-Tab UI differentiator** — without a maintained "what the tool already uses" list, "new" vs "used" badges have nothing to compare against. This manifest should be seeded manually (grep own codebase + human review) before the UI work starts, not generated as an afterthought.
- **Versioned storage and quota handling are shared with Stabilisierung** — the Gamecode-Scan milestone should not re-solve `idbSet()` quota handling; it should consume the fix already scheduled earlier in the roadmap. This is the strongest ordering argument for Stabilisierung → Entflechtung → Gamecode-Scan.
- **Historical diffing conflicts with doing it early** — attempting cross-snapshot diffing before the persistence layer is extracted out of `items.js` (Entflechtung) means building throwaway plumbing twice.

## MVP Definition

### Launch With (v1)

Minimum viable product for the Gamecode-Scan milestone — validates that runtime discovery + diffing actually surfaces useful, previously-unknown hooks.

- [ ] Core global/function probe (known BC identifiers: `Player`, `ChatRoom`, `ServerSend`, `InventoryXxx`, `CharacterXxx`, …) — the entire premise of the feature
- [ ] Asset catalog property extraction (groups, item properties, locks, colors, layers) beyond what's already cached — needed to find bot-action opportunities, the stated goal
- [ ] Chat hook enumeration (`ChatRoomRegisterMessageHandler` presence + any readable handler registry) — bots are chat-driven; this is the other half of "the entire premise"
- [ ] `bcModSdk.getModsInfo()` + `bcModSdk.getPatchingInfo()` read — highest value-per-line-of-code discovery source available, verified stable API
- [ ] Known-mod fallback probes for BCX (`window.bcx`), MBS (`globalThis.mbs`), and LSCG (existing `LSCG_DB` reclassified as "already used") — without this, the SDK-only view misses two of the four mods named in PROJECT.md
- [ ] "Already used by tool" static baseline manifest, seeded once, checked in
- [ ] Read-only enforcement (no function invocation, ever) — non-negotiable per Anti-Features
- [ ] Versioned snapshot storage (new timestamped entry per scan, no auto-overwrite)
- [ ] Manual delete of a snapshot with confirmation dialog
- [ ] Visible quota-exceeded error on scan save
- [ ] Scan-Tab UI: searchable/filterable list with "used" vs "new" badges, grouped by category (Globals / Asset Properties / Chat Hooks / Mods)

### Add After Validation (v1.x)

- [ ] Suggested bot actions/triggers generated from "new" scan entries — add once the baseline diff itself is proven useful and the author has a feel for which "new" entries are actually worth turning into bot features
- [ ] Per-mod compatibility badges in the Bot Editor — add once bots start actually depending on mod-specific actions discovered via the scan
- [ ] WCE/FBC-specific fallback probe — add once the actual global name is confirmed by a live console check (see Gaps below); don't guess and ship a probe that silently never matches

### Future Consideration (v2+)

- [ ] Hooked-function conflict view (tool's own EXEC watchers vs mod hooks) — defer until the tool's own bot-engine watchers have caused a real, observed conflict; speculative before then
- [ ] Historical scan diffing (snapshot-to-snapshot changelog) — defer until persistence-layer extraction (Entflechtung) lands and there are at least two real snapshots far enough apart in time to make a diff meaningful

## Competitor Feature Analysis

There is no direct competitor to "runtime BC game-API inventory + diff" as a standalone tool — the closest comparators are (a) how other BC mods discover/coexist with each other, and (b) generic API-diff tooling outside the BC ecosystem.

| Feature | bcModSdk / BC mod ecosystem | Generic API-diff tools (oasdiff, OpenAPI Diff Viewer) | Our Approach |
|---------|--------------------------|--------------------------------------------------------|--------------|
| Mod/API enumeration | `bcModSdk.getModsInfo()` gives name/version/repo for SDK-registered mods only; BCX/MBS additionally self-expose `window.bcx`/`globalThis.mbs` | N/A (compares two static spec files, not a live runtime) | Combine `bcModSdk` registry + curated known-mod probes, since no single registry is complete |
| Hook/function claim visibility | `bcModSdk.getPatchingInfo()` shows which functions are hooked and by whom, to help mod authors avoid stepping on each other | Diff shows added/removed/changed endpoints between two spec versions | Surface hook claims read-only as *context* (avoid EXEC-injected watcher conflicts), not to compete for hooks ourselves |
| "New since last look" UI | MBS ships a dedicated screen listing items added in the current BC version — same underlying idea (diff against a known baseline), but scoped to wardrobe items only | Core feature: grouped, filterable added/removed/changed list, copy-to-clipboard summary | Generalize MBS's own pattern (already validated among BC power users) to *all* discoverable API surface, not just wardrobe items |
| Safety posture toward unknown surface | Mods generally only call functions whose behavior their author already tested manually; no ecosystem tool auto-fuzzes BC functions | N/A | Explicit anti-feature: never invoke, only reflect (see Anti-Features) |

## Concrete Browser-Console Commands (Manual Verification / Loader Reference)

The user can run these directly in the BC game tab's console today to sanity-check what the loader's scan should later automate. All are read-only.

```js
// 1. bcModSdk mod registry (name/version/repo for every SDK-registered mod)
window.bcModSdk ? bcModSdk.getModsInfo() : 'bcModSdk not loaded';

// 2. bcModSdk hook/patch registry (which game functions are already hooked, and by whom)
window.bcModSdk ? [...bcModSdk.getPatchingInfo().entries()] : 'bcModSdk not loaded';

// 3. BCX presence + version (BCX exposes its own global independent of bcModSdk)
typeof window.bcx !== 'undefined'
  ? { version: bcx.version, versionParsed: bcx.versionParsed, isDevel: bcx.isDevel }
  : 'BCX not loaded';

// 4. MBS presence + version (MBS exposes its own global independent of bcModSdk)
typeof window.mbs !== 'undefined'
  ? { version: mbs.MBS_VERSION, apiMajor: mbs.API_VERSION && mbs.API_VERSION.major }
  : 'MBS not loaded';

// 5. LSCG presence (already consumed by this tool's existing outfit-scan feature — treat as "used", not "new")
typeof window.LSCG_DB !== 'undefined' ? 'LSCG_DB present' : 'LSCG_DB not found';

// 6. Broad fallback sweep for mod-added globals whose exact name isn't confirmed yet (e.g. WCE/FBC)
//    Run this to find candidate globals, then add confirmed names to the known-mod probe list.
Object.keys(window).filter(k => /^(WCE|FBC|LSCG|MBS|BCX|Responsive|Ultra)/i.test(k));

// 7. Core BC chat-hook API presence (confirmed core function, not a mod addition)
typeof window.ChatRoomRegisterMessageHandler === 'function'
  ? ChatRoomRegisterMessageHandler.toString().slice(0, 200)
  : 'not found in this BC version';

// 8. Asset catalog shape sanity check (property names present on a sample asset/group)
Array.isArray(window.Asset) && Asset.length
  ? Object.keys(Asset[0])
  : 'Asset[] not found';
```

Run commands 3, 4, and 6 with the relevant mod (BCX, MBS, WCE) actually loaded in that session — a `typeof … !== 'undefined'` check only tells you the mod is loaded *and initialized before the check ran*, not that the mod is absent if `undefined` (it may just not have finished loading yet).

## Gaps / Open Questions

- **WCE/FBC exact global name not confirmed.** Docs pages describe features but not the technical integration surface. Before shipping a WCE-specific probe, run console command #6 above with WCE actually loaded and confirm the real global name(s) — do not guess and ship a probe that silently never matches (a false "not detected" is worse than no probe at all, since it would misclassify an active mod as absent).
- **`bcModSdk.getModsInfo()` is not a complete mod census.** It only lists mods that call `registerMod()`. BCX and MBS are confirmed to additionally (or instead) expose their own dedicated globals (`window.bcx`, `globalThis.mbs`), which is why the known-mod fallback probes are table stakes, not optional polish. Any other mod that neither uses bcModSdk nor exposes a documented global will be invisible to this scan design — acceptable for v1 given the four mods explicitly named in PROJECT.md are all covered by SDK-registry-or-fallback-probe.
- **Whether BCX itself registers with bcModSdk in addition to exposing `window.bcx`** could not be confirmed from public docs alone; treat `window.bcx` as the authoritative BCX detection path regardless.
- **Live verification still required.** All console commands above should be run once by the user in an actual game tab (with LSCG/BCX/MBS/WCE loaded, per PROJECT.md's note that the user can execute and return console output) before the scan feature's probe list is finalized — this document establishes what to check, not a substitute for that live check.
